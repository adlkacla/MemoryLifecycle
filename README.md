## Условия запуска:

```bash
dotnet run --project src\MemoryLifecycle\MemoryLifecycle.csproj
```

## Выводы:

1. **Gen0 нагружают мелкие короткоживущие объекты**: 12.21 МБ аллокаций дали 2 сборки Gen0, а Gen2 не потребовался —
   объекты умирают молодыми.
2. **Gen2 нагружает только полная сборка**, и её переживают долгоживущие данные: после принудительного Gen2
   в куче остались 0.52 МБ из статического списка (`Heap Δ`), а крупные массивы из локального списка были собраны.
3. **LOH не всегда приводит к немедленной сборке**: крупные массивы (> 85 000 байт) сразу попадают в LOH и не
   расходуют бюджет Gen0, но счётчик Gen2 растёт только при сборке Gen2, а бюджета LOH хватило.

# КТ №41. Параллельная и фоновая сборка мусора

## Результат:

На персональных компьютерах лучше использовать режим Workspace в сборщике мусора, иначе будет неэффективное использование ресурсов компьютера

## Выводы:

1. Режим GC переключился (GCSettings.IsServerGC = False / True), а работа одинакова: 146,49 МБ и одна и та же контрольная сумма (152985664). Сравнение корректно.

2. Больше сборок Gen0 в Server GC не означает деградацию. У каждой кучи свой бюджет Gen0, а DATAS (включён по умолчанию) делает бюджет пропорциональным объёму живых данных, здесь он почти нулевой. Число сборок (Gen0 29–32, Gen1 5, Gen2 4 против 24/1/0 у Workstation) зависит от конфигурации куч, а не только от нагрузки. Чтобы проверить это, нужен прогон с DOTNET_GCDynamicAdaptationMode=0. Я не проверял, как DATAS повлиял на ваш запуск, так что это гипотеза.

3. Server GC не всегда быстрее. На короткой нагрузке (около 146 МБ за десятки миллисекунд) накладные расходы на несколько куч и потоки сборки перевесили выигрыш. Время Server GC выросло с 85,6 до 141,4 мс при фоновой нагрузке, а у Workstation только с 81,6 до 93,0 мс. Пауза принудительного блокирующего Gen2 тоже больше (3,74–6,51 мс против 2,21–2,96 мс), потому что обходятся все кучи. Вывод о преимуществе режима нужно делать по нескольким замерам и длительной нагрузке, а не по одному запуску.
